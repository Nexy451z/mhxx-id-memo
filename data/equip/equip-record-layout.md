# 装備ボックスレコード配置仕様（メモリスキャン補助用）

Monster Hunter XX (Switch) の**装備ボックス 1 レコード 36 バイト**の実バイト配置を、
mhnxeditor のソースと実セーブ 2 本で確定したもの。数値はすべて実データで確認済み。

- 機械可読版: `equip-record-layout.json`（`tools/verify_equip_record_layout.py --json` が生成）
- 検証スクリプト: `tools/verify_equip_record_layout.py`
- 検証結果: **PASS**（2 セーブ / 3 スロット / 使用 2,350 レコード）

> このファイルは説明用。数値の正は JSON と検証スクリプト側。

---

## 1. セーブファイル内の位置

```
ファイル (4,726,188 B)
├─ +0x00000  36 B    Switch セーブヘッダ
└─ +0x00024  ...     body (4,726,152 B)
   ├─ +0x00010  u32le  slot 0 base（body 先頭からの相対）
   ├─ +0x00014  u32le  slot 1 base
   ├─ +0x00018  u32le  slot 2 base
   ...
   └─ slot base + 0x62EE  装備ボックス 2000 枠 × 36 B = 72,000 B
      slot base + 0x17C2E  オトモ装備ボックス（1000 枠 × 36 B）
```

- 実測値（両セーブ共通）: slot base = `0x126474 / 0x244C34 / 0x3633F4`
- slot stride = `0x11D088`（キャラ本体）+ `0x1738`（フッタ）= **`0x11E7C0`**
- 装備ボックスの body 相対オフセット = `0x126474 + 0x62EE = 0x12C762`、ファイル絶対 = **`0x12C786`**

**stride は計算せず、body+0x10/0x14/0x18 の 3 つのポインタを読む方が安全**（MHGU では 1 バイトずれる既知の差がある）。

## 2. レコードのバイト配置

```
+0x00  u16le  head word
       bit  0..4   type            (0=空き, 1..5=防具, 6=護石, 7..21=武器, 12 は未使用)
       bit  5..9   level - 1
       bit 10..14  transmog_level - 1
       bit 15      未使用（実セーブ 2,350 レコードで 0）
+0x02  u16le  id                 防具=series_id / 武器=武器種ごとの weapon_index
+0x04  u16le  transmog_id        着せ替え元の装備 ID（0 = なし）
+0x06  u16le  deco1              装飾品 1 のアイテム ID（0 = 空き）
+0x08  u16le  deco2
+0x0A  u16le  deco3
+0x0C  ...    tail（24 バイト）
              type 6  = 護石ブロック（§4）
              type 20 = 猟虫ブロック
              それ以外 = 通常 0（ただし前の持ち主のバイトが残ることがある → §7）
```

### head word の読み方

```python
head = rec[0] | (rec[1] << 8)
type            = head & 0x1F
level           = ((head >> 5) & 0x1F) + 1
transmog_level  = ((head >> 10) & 0x1F) + 1
```

**レベルは -1 して格納されている**（5 ビット幅なので 1..32）。
bit 5 から上をまとめて読むと着せ替えレベルが混ざる（equip.rs の doc コメントが同じ間違いを記録している）。

### 空き枠の判定

36 バイトが**すべて 0** のレコードが空き。type だけ 0 で他のバイトが残っているレコードもあり得るので、
「type == 0」だけで空きと判断しない（書き込み前に全バイト 0 を確認する）。

| 3 | 防具（腕） | series_id | `armor_id = id*5 + 2` |

## 4. 護石（type 6）のレコード

```
+0x00  u8   0x06               常に（type 6 / level 1）
+0x01  u8   0x00               常に
+0x02  u8   kind               護石の種類 1..10（amuletData_jpn.gmd の行）
+0x03  u8   0x00               常に
+0x04  u16  0x0000             常に（着せ替え ID の位置だが護石では未使用）
+0x06  u16  deco1              挿してある装飾品のアイテム ID（0 = 空き）
+0x08  u16  deco2
+0x0A  u16  deco3
+0x0C  u8   skill1_id          スキル 1 のスキル ID（skills.csv の skill_id、0 = なし）
+0x0D  u8   skill2_id          スキル 2 のスキル ID
+0x0E  i8   skill1_points      スキル 1 のポイント（符号あり）
+0x0F  i8   skill2_points
+0x10  u8   slots              この護石の装飾品スロット数 0..3
+0x11  u8   0x00               常に
+0x12  u8   rarity             レア度 97..100
+0x13  u8   0x01               常に
+0x14  ...  0x00               常に（16 バイト）
```

- `+0x12/+0x13` は u16 で読むと**護石アイテム ID 353..356**（`0x161..0x164`）。下位バイトがレア度、上位が常に 1。
- `+0x02` の kind は `TALISMAN_RARITY` でレア度に結び付く（1-2→97, 3-4→98, 5-7→99, 8-10→100）。
- 護石のスキル ID は **`skills.csv` のスキル ID**（0 始まりのスキルツリー ID）。650 件すべてが解決した。

### 実測（サンプルセーブ 650 件）

| フィールド | 観測値 |
|---|---|
| `+0x00` | 650/650 が `0x06` |
| `+0x01` / `+0x03` / `+0x11` | 650/650 が `0x00` |
| `+0x02` kind | 0:2, 4:2, 6:20, 7:46, 10:580 |
| `+0x10` slots | 0:32, 1:10, 2:18, 3:590 |
| `+0x12` rarity | 98:2, 99:68, 100:580 |
| `+0x13` | 650/650 が `0x01` |
| `+0x12/+0x13` u16 | 354:2, 355:68, 356:580（すべて 353..356） |
| `+0x06..+0x0B` | 15/650 が非 0（装飾品 ID）。非 0 の個数は `+0x10` を超えない |
| `+0x14..+0x23` | 650/650 が全 0 |

## 5. 装飾品フィールド（+0x06 / +0x08 / +0x0A）

- 値は**装飾品のアイテム ID（2638..2899）**、0 が空き。
- **type 1..5（防具）/ 6（護石）/ 7..21（武器）のすべてで同じ意味**。
- 装飾品はサイズ（1..3）に関係なく **1 枠に 1 個**。3 スロットの珠でも `[id, 0, 0]` のように先頭から詰める。
- 非 0 の個数は装備のスロット数を超えない。実測:
  - 防具 48 レコード … `armorSeriesData.asd` の `+108+part` のスロット数を超えない（超過 0）
  - 護石 15 レコード … `+0x10` のスロット数を超えない（超過 0）
  - 武器 … 未検証（`weaponNNLevelData` のスロット数を読んでいない）

## 6. ページ幾何（エディタの一覧）

| 項目 | 値 | 出典 |
|---|---:|---|
| 1 ページの枠数 | **9** | `hbedit.rs` の `page_move` の doc「the equipment box shows nine and a warning strip takes one」 |
| 行の高さ | 56 px | `tests/scroll_ui.rs`「The track the equipment box uses: nine 56px rows.」 |
| スクロールトラック | 504 px = 9 × 56 | 同上（`TRACK = 504`） |
| ページ数 | **223** = ceil(2000 / 9) | 計算 |
| 最終ページ | page 222 = index 1998..1999（2 枠） | 計算 |

```
page p (0 始まり) -> index [p * 9, min(p * 9 + 9, 2000))
index i           -> page i // 9, 行内位置 i % 9
```

**これはエディタの一覧画面のページ**。ゲーム本体の装備ボックス画面が 1 ページ何枠かは、
手元の資料からは確定できなかった（§8 の unknown）。

## 7. メモリスキャンのしかた（実用メモ）

1. **セーブバッファを持っている場合**: `body + u32(body+0x10) + 0x62EE` が装備ボックスの先頭。
   そこから 36 バイト刻みで 2000 枠。
2. **アドレスだけ分かっている場合**: 見つけたレコードのアドレスを `A`、その枠番号を `i` とすると、
   ボックス先頭 = `A - i*36`、slot base = `A - i*36 - 0x62EE`。
   36 バイト境界が分からないときは、`A` から 0..35 バイトずらして
   「type が 1..21 に収まる」位置を探す。
3. **既知の装備から探す場合**: 例えば レザーヘッド（type 1 / id 1 / Lv1 / 着せ替えなし / 装飾品なし）は
   36 バイトが `01 00 01 00 00 00 00 00 00 00 00 00` + 24 × `00`。
   ただし同じ形のレコードは他にもあるので、**36 バイトの並びが続くこと**（隣接レコードの type も妥当か）まで見る。
4. **注意**: `+0x0C` 以降は type 6/20 以外でも非 0 のことがある（§8）。テールを 0 と仮定した
   パターン検索は取りこぼす。

## 9. 不明点（unknown）

1. **ゲーム本体の装備ボックス画面の 1 ページあたりの枠数**。エディタの一覧は 9 行（§6）だが、
   ゲーム内の画面が何枠かは資料から確定できない。
2. **護石の `+0x02` kind = 0 が 2 件だけ観測**され、レア度 99 と結び付いている。
   `TALISMAN_RARITY` の表（kind 5..7 → 99）に無い組み合わせで、意味は不明。
   （サンプルセーブの slot 1 と slot 2 の index 1629 に同一のレコードがある）
3. **護石以外の type でも `+0x0C` 以降が非 0 のレコードがある**（サンプルセーブで 15 件）。
   値は護石ブロックや猟虫ブロックの形をしており、前の持ち主のバイトが残っていると見られる。
   どの操作で残るのかは未確定（エディタの type 変更が原因の可能性がある）。
4. **武器の装飾品数が武器のスロット数を超えないかは未検証**（`weaponNNLevelData` のスロット数を読んでいない）。
5. **type 22 以上がハンターの装備ボックスに現れるかは未確認**（2,350 レコードでは 21 が最大）。
   オトモ装備ボックスは別領域（`0x17C2E`）で、type 22/23/24 を使う。
6. **head word の bit15** は 2,350 レコードで 0 だったが、ゲームが将来使うかは不明。
7. **`+0x02` の id が 0 のレコード**（type 1..5 / 7..21）は観測していない。id 0 が有効かは未確認。
